# CloudBridge V2 阶段二至五正式重构计划

## 1. 状态与启动门禁

所有者已于 2026-08-04 授权启动正式重构。当前已在本地完成阶段二的第一批基础代码，但尚未连接正式前端路由、推送或部署；因此不能表述为线上可用。

正式重构继续遵守 Sites-only：`apps/sites` 是唯一生产 Worker，`apps/storefront` 与 `apps/admin` 是前端源码，`packages/contracts` 保存共享类型；结构化数据使用 Sites D1，媒体使用 Sites R2。

本轮授权包含不同商品去重的人工多商品订单基础、`order_items` 与完整高熵订单号查询；仍不包含数量、持久化或跨设备购物车、会员、在线支付、Webhook、自动退款、资金对账、自动发货、自动续费、自有域名或站内中转站控制台。联系方式查询仍须先完成独立所有权验证后另行实施。

## 2. 当前可复用基础

| --- | --- | --- |

阶段二只做前向新增和兼容扩展，不删除当前 21 张表中的数据或旧字段。

## 3. 阶段二——共享契约、D1 与 API

订单查询拆成三个边界清楚的入口：本机订单使用客户端安全摘要且不读取服务器；订单号查询已在本地正式 API 中实现 `POST`、完整高熵订单号、统一未匹配响应、`no-store`、HMAC 标识和 D1 防刷；联系方式查询仍失败关闭，必须先完成独立的所有权验证，联系方式本身不能直接枚举订单。当前正式响应只返回商品、金额、稳定状态、脱敏联系方式和创建/更新时间，不返回完整联系方式、内部备注或订单历史。

### 3.0 当前本地实施状态

- [x] 共享枚举与 V2 商品、广告、Skill、人工多商品订单和订单号查询契约。
- [x] 前向 D1 迁移：两级分类、商品展示面、广告扩展、Skill、`order_items` 和查询限流记录；保留现有商品、分类和订单 ID。
- [x] 公开目录、广告与 Skill 只读接口，以及不同商品人工订单和安全订单号查询接口。
- [x] 后台两级分类、商品展示面、广告扩展、Skill 与三个广告开关接口；权限、审计和版本冲突沿用现有机制。
- [ ] 正式前台与后台页面连接这些接口并移除相应预览标识。
- [ ] 联系方式所有权验证、正式本机订单摘要持久策略、生产迁移演练与部署。

### 3.1 共享枚举

先在 `packages/contracts` 增加稳定枚举，代码值使用英文：

- `ProductSurface`：`HOME`、`TRANSIT_SUBSCRIPTIONS`、`AI_RECHARGE`
- `PlatformKey`
- `TransitPlanType`
- `BannerPlacement`：与三个 `ProductSurface` 一致
- `BannerTargetType`
- `SkillResourceType`：`SKILL`、`PLUGIN`、`CONNECTOR`
- `SkillSourceLevel`：`OFFICIAL`、`COMMUNITY`

枚举、接口和数据库字段不得依赖中英文显示文案。金额与汇率继续使用十进制字符串和整数运算。

### 3.2 D1 前向迁移

先为现有 `categories` 增加可空 `parent_id`：一级分类的 `parent_id` 为空，二级分类必须指向一个一级分类。API 和数据库校验必须强制最多两级、禁止自引用和循环引用。`products.category_id` 在正式切换后只能引用二级分类。

兼容迁移不得重建或替换现有分类 ID、商品 ID 或商品关联。为每个现有分类新增对应一级分类，再把原分类作为二级分类回填父级；商品继续引用原分类 ID，因此迁移前后的商品关联保持不变。迁移必须先演练父级回填、重复执行、版本冲突、权限、审计和回滚，不在阶段一预览中执行。

新增 `product_surfaces`，至少包含：

- `id`
- `product_id`
- `surface`
- `sort_order`
- `is_visible`
- `created_at`
- `updated_at`
- `version`

约束 `product_id + surface` 唯一；同一商品可以出现在多个页面，但不能复制商品主记录。现有商品幂等回填 `HOME`。

为现有商品增加两个可空字段：

- `platform_key`
- `transit_plan_type`

扩展现有 `heroes`，兼容期保留 `image_key` 与 `target_slug`，新增：

- `placement`
- 手机图片字段
- `target_type`
- 主目标值
- 次按钮中英文、目标类型与目标值

现有 Hero 幂等回填 `HOME`。旧字段在兼容期继续可读，不在本阶段删除。

新增四张 Skill 表：

- `skill_categories`
- `skill_category_translations`
- `skills`
- `skill_translations`

Skill 内容至少包含稳定 slug、分类、资源类型、来源级别、维护者、GitHub URL、文档 URL、许可证、兼容环境、核验日期、启停、排序、版本、创建和更新时间。Skill 不进入商品、价格、库存或订单表。

在现有设置 JSON 中增加三个广告开关，键与 placement 一一对应。迁移默认值必须保持当前正式页面行为。

### 3.3 公开只读 API

- 扩展 `GET /v1/products`，支持 `surface`、`category`、`platform`、`transitPlanType`、`search`。
- 扩展 `GET /v1/categories`，支持 `surface` 并返回最多两级的稳定树；`全部商品` 不进入响应数据。
- 新增 `GET /v1/banners?placement=`。
- 新增 Skill 分类、列表和详情接口。
- 扩展 storefront config，返回三个广告开关，但不把阶段一 fixture 混入正式响应。

公开接口只返回已启用且允许公开的记录，支持双语回退、稳定分页、明确空状态和缓存键。商品查询继续应用现有库存、币种和陈旧汇率门禁。

### 3.4 后台 API

- 扩展现有分类接口，管理可空 `parent_id`，拒绝三级和循环引用，并保留权限、版本冲突与审计。
- 扩展现有商品接口，管理二级 `category_id`、`product_surfaces`、`platform_key` 与 `transit_plan_type`；后台按一级到二级级联选择，写入时只提交二级分类 ID。
- 扩展现有 Hero 接口，管理 placement、手机图、目标和次按钮。
- 扩展设置接口，管理三个广告开关。
- 新增 Skill 分类和内容管理接口。

所有写入继续使用现有角色权限、期望版本、冲突失败、事务或 D1 batch、业务原因与审计。保存成功必须重新读取已提交状态；不得用前端计时器模拟成功。

## 4. 阶段三——正式页面接入

1. 将阶段一组件拆成纯 View 与 Live Container；View 不直接访问 API，正式容器使用真实接口，预览容器继续使用 DEMO fixture。
2. 上线未来正式路由：`/:locale/transit-subscriptions`、`/:locale/ai-recharge`、`/:locale/skills`、Skill 详情和需要的商品详情兼容路径。
3. 正式路由全部通过后，网站主导航仍只放网站级目的地；中转站与 AI 服务继续通过两级商品分类和展示面进入，不得与主导航重复。
4. 后台“内容与展示”组增加 Skill 推荐入口，同时保持九个一级入口、每组最多四页和同一权限过滤。
5. 完成 SEO、canonical、hreflang、Open Graph、sitemap、加载、错误、空和 404 状态。
6. 每个页面只有取得真实读取或写入证据后，才移除对应预览提示；不得静默回退到 DEMO 数据。

## 5. 阶段四——正式图片

布局经人工确认后，分别规划首页、中转站、AI 代充、商品模板和 Skill 视觉。图片进入既有媒体与 R2 引用体系；标题、正文和按钮继续由 HTML 输出，不把关键文字烘焙进图片。

阶段四开始前需再次确认图片范围、生成方式、版权与媒体引用，不在阶段一擅自生成正式素材。

## 6. 阶段五——验收与上线准备

- 完整迁移演练与全新 D1 初始化，验证前向迁移、唯一约束、回填幂等和备份兼容。
- 验证分类最多两级、父级停用影响、无循环引用、商品只引用二级分类，以及商品状态、库存、币种、分类、surface、平台与套餐类型联合过滤。
- 验证 Hero 三 placement、三个开关、手机图、目标与旧字段兼容。
- 验证 Skill 外链主机白名单、翻译回退、无效链接、角色权限、版本冲突和审计。
- 浏览器覆盖 1440、1024、768、390、320px，以及中英文、深浅主题、键盘、触摸、减少动态、控制台和网络。
- 运行全部受影响测试、`npm run check` 与 `npm run build:sites`。

Git 提交、推送、PR、Sites 保存版本或生产部署必须重新取得明确授权。只有生产部署状态、匿名 HTTP/浏览器结果和真实数据重新读取都成功，才可写“正式上线”。

## 7. 回滚与兼容原则

- 迁移只新增表、索引或可空/安全默认字段；不在同一版本删除旧数据、旧字段、订单、媒体或审计记录。
- `product_surfaces` 与 Hero 回填必须可重复执行且结果一致。
- 新导航由已提交配置控制；异常时先回退导航或关闭对应广告，不回滚订单数据。
- Skill 没有正式记录时返回诚实空状态，不内置会被误认为生产内容的样例。
- 兼容期结束和旧字段删除必须作为独立迁移再次评审。

## 8. 正式完成定义

某一 V2 能力只有同时满足以下条件才算正式完成：

1. 共享契约、D1、API、后台和前台使用同一真实模型。
2. 加载、错误、空、校验、移动端和基础无障碍完整。
3. 权限、审计、版本冲突、缓存、迁移和回滚经过测试。
4. 对应正式路由不再使用 fixture，并移除预览提示。
5. `npm run check` 与 `npm run build:sites` 通过。
6. 取得真实部署和匿名访问证据。
7. 交付报告继续列出支付、对账及其他冻结能力，不把未来计划写成当前事实。
