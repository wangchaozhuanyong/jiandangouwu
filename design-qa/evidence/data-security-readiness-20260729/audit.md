# 数据安全真实化设计审查

## 审查范围

- 页面：正式管理后台 `/admin/data-security`
- 用户目标：确认当前应用已经执行哪些数据保护控制、哪些运行证据可读取，以及上线前还缺少哪些数据治理能力
- 证据：本轮真实浏览器截图 `01-current-preview-viewport.png`、`02-real-readiness-desktop.png`、`03-real-readiness-mobile-390.png`、`04-real-readiness-mobile-table-390.png`、`05-real-readiness-mobile-320.png` 与 `06-before-after-comparison.png`

## 步骤 01：当前数据安全设计预览

- 健康状态：视觉结构稳定，但治理真实性不合格
- 优点：四张分类卡和保留策略表层级清楚，信息扫描路径短，页面只有一个主标题。
- UX 风险：页面把“订单关闭后 30 天”“审计 365 天”“日志 90 天”以及“已覆盖”作为确定状态，但仓库没有已经批准并执行的保留、删除、匿名化或系统日志治理策略；策略检查按钮也只打开模拟流程。这会让管理员误以为数据保留与删除已经生效。
- 逻辑风险：“个人信息”卡包含设备数据，但当前正式订单模型没有设备字段；“系统运行日志”没有可查询的本地持久化领域；“不可变记录”也不能由当前普通 MySQL 审计表单独证明。
- 无障碍限制：截图能确认标题、间距、对齐和颜色层级，但不能证明键盘顺序、屏幕阅读器名称、焦点状态和缩放重排。
- 建议：保留当前四类信息密度，但把它们改成“当前代码边界”，明确哪些控制已实现、哪些只是未批准的治理规划；删除虚构保留天数和策略检查流程，使用真实会话/RBAC状态、最近审计记录和明确的 `NOT_DEFINED` / `NOT_IMPLEMENTED` 上线门禁替代。

## 步骤 02：真实桌面就绪中心

- 健康状态：通过
- 页面保留一个顶栏 H1，首屏按“真实性说明 → 四项状态摘要 → 只读操作 → 四类当前代码边界”的顺序扫描；原来的模拟提示、策略检查、已覆盖标签和虚构保留期限已移除。
- 当前会话、五项代码控制、最近审计样本和五项治理门禁使用不同视觉层级，不把代码存在、运行记录和政策批准混成一个成功状态。
- 1280 × 720 验收中页面根宽 1265px，不存在页面级横向溢出；所有可见按钮均不小于 44 × 44px，页面只有一个 H1。

## 步骤 03：真实行为与双语

- 健康状态：通过
- “刷新审计证据”只重新读取 `GET /v1/admin/audit?page=1&pageSize=100`；“打开安全事件”正确进入 `/admin/security-events`，返回后页面状态正常。
- 中文与英文均显示完整真实性边界，英文视口根宽仍为 1265px，没有因为长文案形成页面级横向溢出。
- 当前一次性 QA 角色只有 `audit.read`，页面读取到 12 条最近审计样本，其中 2 条拒绝或失败、1 条联系方式揭示；页面未读取审计前后差异、IP 哈希或认证内部字段。

## 步骤 04：390px 与 320px 响应式

- 健康状态：通过
- 390px 视口根宽 375px，320px 视口根宽 305px，均没有页面级横向溢出、标题裁切或操作重叠；摘要、工具栏、代码边界、会话证据和治理门禁按单列自然重排。
- 严格单行审计表在 390px 的 349px 容器内保留 1338px 内容宽，在 320px 的 279px 容器内保持相同内部滚动边界；第一列吸附，页面本身不被表格撑宽。
- 移动端可见操作保持至少 44px 高。截图不能单独证明所有键盘与屏幕阅读器路径，语义名称、焦点轮廓和内部滚动还由 DOM 与静态测试共同覆盖。

## 步骤 05：同视口前后对照与最终判断

- 健康状态：通过
- `06-before-after-comparison.png` 使用相同 1265 × 712 页面视口并排比较。改造后延续原后台的浅色卡片、深色侧栏、青色动作与紧凑信息密度，没有引入新的设计语言。
- 旧版的视觉整齐建立在虚构保留期限与覆盖状态上；新版把相同空间改为可核验的代码控制、会话和审计证据，并把未定义、未开发、未连接分开表达，信息层级更符合管理员决策。
- 最终未发现 UI 重叠、内容裁切、页面级横向溢出、重复主标题或设计系统冲突。控制台只有 Vite/React 开发提示，没有 warning 或 error。
